# Database Infrastructure

Shared PostgreSQL persistence foundation. Prisma 7.9.1 is the production-default ORM/runtime; the explicit Legacy pg runtime remains only for active-query cancellation compatibility and tests. The historical project SQL migration runner remains the single deployment history. Each module owns its PostgreSQL schema area, Prisma Schema source fragment, repositories, and mappings; this package must not become a cross-module query layer or a registry of all application tables.

Public exports must not expose module table definitions or provide a generic repository that bypasses ownership. Application startup never mutates database schemas; reviewed SQL migrations run as a separate deployment step with dedicated credentials.

## Startup compatibility check

Applications may call the public `checkMigrationCompatibility` API with a caller-owned runtime/read-only PostgreSQL pool, the complete release migration-directory catalog, and an independently governed `applicationSchemaVersion` in strict `x.y.z` form. The caller owns connection, query/statement and overall startup deadlines, cancellation and pool shutdown; the database package deliberately provides no connection-string convenience entry point that could create an unbounded pool. The schema version is not a release/build identifier: values such as the four-segment `AI_CRM_RELEASE_ID=2026.07.26.1` must never be passed as `applicationSchemaVersion`. The check issues exactly one `SELECT` against `ai_crm_migrations.applied_migrations`; it does not acquire the migration lock, start a transaction, execute SQL migrations, or write migration state. It fails closed in its report when a required migration is missing, an applied migration is unknown to the release, registry identity/checksum differs, compatibility evidence is unavailable, or the application schema version is outside the reviewed range. Database/query failures are thrown so the composition root can mark startup/readiness unavailable without mistaking an unavailable check for compatibility.

New migration metadata must express `applicationCompatibility` as `{ "minimumInclusive": "x.y.z", "maximumExclusive": "x.y.z" }`, with `maximumExclusive` optional. The loader exposes the normalized object as `applicationCompatibilityRange`; the pre-existing string-typed `MigrationMetadata.applicationCompatibility` remains available (deprecated) so this new database API does not silently break consumers. Historical metadata and SQL remain unchanged, and the loader adapts only the historical `">=0.0.0"` value plus the three repository-existing additive declarations; every other free-text value is rejected.

Migration `0000000011` additively extends the registry with persisted minimum-inclusive and optional maximum-exclusive application schema compatibility evidence. It backfills versions `0000000001` through `0000000010` only when each persisted SQL checksum matches its reviewed value; mismatch aborts the migration transaction. The migration runner persists the normalized range for `0000000011` and every later migration. Runtime compares this database evidence with the release metadata and fails closed on absent or mismatched evidence, so changing `.meta.json` alone cannot silently change a compatibility conclusion. A release must include the complete migration catalog; unknown applied migrations also fail closed instead of guessing rollback safety.

`DatabaseRuntime` exposes parameterized `execute` and nested `withTransaction` operations without exposing a PostgreSQL client, ORM query builder, or transaction handle. The default Prisma implementation preserves this public neutrality and rollback-only nested transactions; `PrismaClient` and `Prisma.TransactionClient` remain private implementation details. Prisma does not advertise active-query interruption: signals are checked before/after execution and the configured PostgreSQL `statement_timeout` bounds an in-flight query.

The explicit Legacy PostgreSQL runtime advertises `abortSignalSupport: true`. It remains available only where active statement interruption itself is the capability under test. Production composition uses Prisma and must not infer that pre/post signal checks can terminate an already executing provider query.

The root `pnpm db:migrate` command discovers versioned SQL migrations under `packages/database/migrations` and each `packages/crm-modules/*/migrations` directory, then applies the combined list in global version order under the migration lock. Module `migrate` commands remain available for isolated ownership tests; deployment uses the root command.
