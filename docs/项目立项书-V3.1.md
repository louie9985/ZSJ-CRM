## 一、项目背景与立项目的

现有CRM在客户信息、销售过程、履约与财务责任边界、复购管理上分散且不透明：客户资料多头维护缺乏统一主档案；销售环节缺少统一的分配/接单/超时规则，责任难以追溯；报名审核与财务确认之间责任边界不清；学员服务与复购缺乏系统化流程；管理层缺少一条从客资到复购的全生命周期漏斗视图。

本项目要解决的不是"换一套软件界面"，而是**把公司的组织责权利关系，用系统规则固化下来**：谁能看什么数据、谁能做什么决策、谁对什么结果担责、谁因什么结果获得激励，全部由系统统一判断和留痕，不再依赖人工口头约定或Excel台账。

**立项目的**：以AI-CRM V3.0系统建设为载体，完成组织责权利体系与系统架构的一次性对齐，2026-08-31硬切换替代老CRM，为后续从"客户经营系统"升级为"公司经营操作系统"打基础。

## 二、组织架构与责权利体系（顶层设计）

系统的模块划分直接对应组织的部门划分，二者不是两套独立设计，是一套设计的两个投影。

### 2.1 组织五分类

业务组织按职能分为五类，系统模块按此分类组织权限与数据边界：

| 分类 | 涵盖部门/模块 | 责权利定位 |
|---|---|---|
| 增长前台 | 新媒体客资、销售转化 | 对"进来多少、转化多少"负责，不直接决定履约与财务合规 |
| 交付中台 | 报名履约、学生服务交付、考务 | 对"办得对不对、服务得好不好"负责，是复购的利润核心 |
| 监督中台 | 服务质控、财务结算（审核职能） | 对"合规、责任判定、资金安全"负责，评分权与绩效应用权分离，防止监督部门权力过大 |
| 经营支持中台 | 人力资源、行政IT | 对组织运转的支撑负责，不直接背业务指标 |
| 数字产品中台 | 数字产品与AI中台 | 提供系统工具与数据能力，**不对业务结果担最终责任**；编制随营收阶段克制增长，不靠堆人解决管理混乱 |

### 2.2 部门负责人绩效原则（责权利的量化落地）

各部门负责人绩效结构统一为：**80%本部门核心指标 + 10%上下游协同 + 10%跨部门整改/人才培养**。系统需保证：指标上升但投诉率/退款率/毛利/交付质量同时恶化的，不判定为健康达成——即系统统计口径要能同时呈现"结果"和"结果的代价"，而不是单一正向数字堆砌（对应总纲 BR-G04、AP-21事件驱动统计的口径唯一性）。

不同部门是否为"利润中心"决定考核逻辑不同：新媒体、报名履约、考务不直接创收，考核成本与质量；学生服务是复购利润核心，考核复购与服务质量；不能对所有部门一刀切按营收考核。

### 2.3 四级大盘：权限分层即责权利分层

系统的数据可见范围严格对应组织层级的决策权范围，不是技术上的"角色权限配置"，而是组织责权利边界的直接体现：

| 层级 | 看什么 | 对应责任 |
|---|---|---|
| 老板 | 全生命周期漏斗、经营质量、部门贡献排行 | 对公司整体经营结果负责 |
| 总监/部门负责人 | 本部门健康度、上下游协同指标 | 对本部门经营健康负责 |
| 主管/组长 | 团队过程指标（在线率、漏单、SLA） | 对团队过程管理负责 |
| 员工 | 今日待办、个人业绩与排名 | 对个人执行负责 |

同一部门内不同岗位看不同数据（如新媒体一/二/三部页面不同），系统UI与权限差异化由岗位责权利差异驱动，而非反过来。

### 2.4 "人"的建模：组织与客户两套主档案

系统把"责权利"落到数据模型上，分员工侧与客户侧两条对称主线：

- **员工侧**：账号（登录）、员工档案（人事身份）、业务任职（Assignment：某人以某角色在某范围内的任期）三者分开建模。业绩归属按"成交时点"的任职关系判定，不看当前部门——离职、转岗不会改写历史责任归属。
- **客户侧**：自然人主档案、业务身份（客资/客户/学员/外部提交者等）、归属关系（谁负责这个客户，哪个区间）三者分开建模，一人可多重身份，归属可变更但历史可追溯。

这套建模保证一件事：**责任判定永远基于"当时是谁负责"，而不是"现在系统里显示谁负责"**，从根本上避免离职甩锅、转岗甩责的漏洞。

## 三、系统架构（框架层）

系统分"平台底座"和"业务模块"两层，边界铁律：平台不反向依赖业务模块，业务模块之间不得互相直接调用，只能通过统一事件机制交互。这一架构约束直接对应组织上"中台不越权决策业务、业务部门之间不能绕过流程互相甩锅"的责权利要求。

平台底座共七组，各自对应一类组织级的公共能力，业务部门共用、不重复建设：

| 平台组 | 职责 | 对应的组织责权利问题 |
|---|---|---|
| 身份与组织 | 账号、组织架构、功能权限、数据范围权限、敏感信息脱敏、多重客户身份 | 谁能登录、谁能看什么、谁能做什么，统一由后端裁决，前端界面不能代替权限判断 |
| 流程与任务 | 状态机、审批流、任务中心、调度规则引擎、通用工单、工作日历 | 所有审批链路、待办任务统一管理，避免部门私下用微信/Excel走流程导致责任无留痕 |
| 消息触达 | 通知中心、预警中心、公告 | 预警必须有人认领处理，不能发了通知就算完成责任 |
| 数据与配置 | 数据字典、参数配置中心、判重服务、归属服务、编号规则 | 客户归属变更（分配/抢单/唤醒/交接）统一走归属服务，业务代码不得私改负责人字段 |
| 留痕与安全 | 审计日志、对象时间线、统一导入导出、附件管理 | 关键动作、资金变动、权限变动全部留痕可查，支撑责任追溯与申诉 |
| 统计与集成 | 事件总线、指标与快照、排名服务、支付/短信/企微集成、AI网关 | 指标必须由业务事件驱动计算，杜绝跨模块直接读表拼数字导致口径不一致 |
| 前端框架 | 动态权限路由、统一列表/详情组件、待办与通知组件 | 保证Web、内部移动端（企微H5）、外部H5/小程序三端责权利呈现一致，不因端不同而权限不同 |

## 四、模块层（业务模块划分与组织对应关系）

模块划分直接映射业务部门与客户生命周期，共13个业务模块，分三层：

```
主数据层：组织与人员(M1) / 客户主数据(M2) / 产品目录(M3)
业务层（沿客户生命周期）：
  客资中心(M4) → 销售转化(M5) → 订单中心(M6) → 报名履约(M7)
  → 学生服务(M8) → 财务审核(M9) → 质控基础(M10) → 需求工单(M11)
消费层：待办与工作台(M12) / 大盘与报表(M13)
```

每个模块对应一个或多个业务部门的责权利边界：
- **M4客资中心**：新媒体部门责任边界（多入口录入、评级、分配规则、异议仲裁三级流程）
- **M5销售转化**：销售部门责任边界（接单时效、跟进节奏、成交后"可见不可扰"避免越权触达学员）
- **M6订单中心 + M9财务审核**：钱的责权利分离——订单状态由报名履约与财务两道审核关卡把关，任何一方不能单独决定订单最终状态
- **M7报名履约**：履约责任边界（驳回权限分三档，明确哪些必须驳回、哪些可先办后补、哪些要升级审批）
- **M8学生服务**：学习规划师与交付主管责任边界（服务节奏、缓考完整五级审批链、复购归属规则）
- **M10质控基础**：质控评分权与绩效应用权分离，评分证据留痕但最终绩效由人力+业务负责人共同确认，防止监督部门权力过大
- **M12/M13**：待办与大盘不建独立数据源，只消费其余模块产生的事件，保证口径唯一、不同岗位看到的数字互相对得上

## 五、功能层（责权利在具体页面与操作上的落地，摘要）

功能层是模块职责的具体化，本立项书不逐页罗列，只说明责权利落地的通用原则：

1. **谁能看**：数据范围权限（本人/本组/本部门/全公司）由系统统一判断，前端不能通过隐藏按钮代替权限控制。
2. **谁能做**：核心状态、金额、归属、审核结果一律由后端裁决，前端只展示和提示，不能绕过后端直接改状态。
3. **谁担责**：关键动作（抢单、审核、退款、转班）都有前置/互斥/终态保护，防止重复提交或状态回退制造责任真空；关键动作全部记录操作人与时间，支持事后追溯。
4. **谁受益**：外部提交者（兼职/轻创）等非员工角色的可见范围与收益状态单独设计分层可见规则，做到"该看的看得到、不该看的看不到"（如不可见聊天记录与内部备注）。

## 六、业务层（关键业务规则中的责权利，摘要）

业务规则手册（总纲第5章 BR-A~BR-G，共46条）是责权利体系落到具体业务判断的最细颗粒度，立项层面摘录责权利争议最集中的几类：

| 责权利问题 | 规则设计 |
|---|---|
| 漏单谁负责 | 个人漏接扣个人、多人漏接组长连带、全组超时无人承接由部门负责人负责、系统故障不追责——权责边界随漏单原因分级 |
| 客户归属如何变更不引发纠纷 | 分配/抢单/公海/唤醒/转班/交接全部通过统一归属服务处理，带变更原因与操作人，任何模块不能私自改归属字段 |
| 退款责任如何判定 | 责任判定分五类（销售承诺/报名履约/学习服务/产品/个人原因），对应影响不同部门指标，避免退款责任无差别甩给某一方 |
| 销售是否能骚扰学员 | 首购成交后销售"可见不可扰"，只能查看订单状态和业绩确认，不能对学员发起服务触达，交付责任明确移交学服 |
| 复购归属谁的业绩 | 复购由当前规划师成交即归当前规划师业绩，不保留原规划师分成，避免"占着不干活也吃分成"的责权利错位 |
| 质控评分是否等于绩效结果 | 质控可评分出证据，但绩效应用需人力与业务负责人共同确认，避免质控单方面决定他人绩效 |
| 特殊承诺/低价是否有效 | 必须成交前走审批，未经审批的订单履约环节强制驳回，把"事前控权"落到系统强制卡点，而非依赖事后追责 |

## 七、指标层（用什么衡量责权利履行情况）

指标是责权利体系的"计分器"，核心原则：**全部由业务事件驱动计算，任何模块不得跨模块直接读表统计**，保证老板、部门负责人、主管、员工看到的数字互相自洽，不出现"白天看的数和晚上对不上"的信任问题。

指标按组织层级对应：
- **老板层**：全生命周期漏斗（客资→有效→接单→成交→审核→确认→入学→首触/规划→复购）+ 部门贡献排行 + 产品经营排行 + 交付质量 + 预警区
- **部门负责人层**：本部门核心指标（如新媒体的有效客资率、销售的成交率、学服的复购率、质控的SLA达成率）
- **主管/组长层**：团队过程指标（在线接单率、2分钟接单率、10分钟首触率、漏单数）
- **员工层**：个人业绩、排名、今日任务完成率

关键指标的分子分母口径已在业务规则手册中逐条锁定（如7/30/90日成交率、72h首触及时率、规划师饱和度加权公式），杜绝"同一个指标不同人算出不同数字"的责权利纠纷。部分口径（复购率分母、种草达标线等）标记为待老板最终确认事项，见第十节。

## 九、组织与资源投入

- **研发团队**：3名全栈工程师 + AI全量辅助编码（不限量token），无独立测试团队，测试责任下沉到shared-core单元测试与关键链路人工验证。
- **业务侧验收人分工**（对应第二节责权利分层，验收权与日常使用权一致）：客资中心=新媒体负责人；销售转化=销售主管；订单履约=报名服务负责人；财务审核=财务主管；学生服务=交付主管；老板大盘=老板本人。
- **数字产品与AI中台自身编制**：随公司营收阶段克制增长（现阶段3-4人配置为主），明确"不靠堆人解决管理混乱"，中台不对业务结果担最终责任，只提供系统工具与数据能力。
- **预算口径**：本立项书暂不包含具体金额预算（人力成本、云服务器、第三方服务如短信/推送/支付网关费用），如决策会审批需要金额数字，需另行提供或按团队规模测算后补充。

## 十一、验收标准

以下五条端到端主链路作为整体验收基准，每条链路本质是一次完整的责权利闭环验证：

1. 客资→分配→漏接流转→抢单→接单→首触→有效判定→成交录单（验证客资责权利归属规则）
2. 订单→报名驳回→补正→通过→财务确认→佣金冻结→7日解冻（验证资金责权利双重审核规则）
3. 订单→财务确认→退款→佣金扣回→责任判定工单闭环（验证退款责任判定规则）
4. 分班→72h首触→7日规划→服务记录→复购机会→复购单→新班分配（验证学员服务责权利转移规则）
5. 缓考完整五级审批链→转班→原班关单新班开单（验证特殊场景多方会签责权利规则）

各业务模块以第九节列明的验收人签字确认为准；全部通过后进入W8切换周。
