## 第 1 章 技术选型（含理由）

### 1.1 技术栈总表

| 层 | 选型 | 选型理由 |
|---|---|---|
| monorepo | pnpm workspace + Turborepo | 三端 + 后端同仓，shared-core 保证"功能一致"；增量构建快 |
| Web | React 19 + HeroUI Pro（CollectUI）+ HeroUI OSS + Tailwind CSS 4 + ECharts | 采用 CR-12 新设计体系；React 19 与 Tailwind CSS 4 为 HeroUI Pro 的运行要求 |
| 内部移动端（企微 H5） | **Taro + NutUI-React + Tailwind token + Lucide**〔CR-11〕 | 内嵌企业微信工作台；与外部端统一框架、复用 shared-core；H5 无包体积上限，功能对齐 Web。原生 App（RN/Expo）已废弃 |
| 外部提交端 | **Taro（React 语法 + NutUI-React）** | 30 秒极简提交场景；一套代码出 H5 + 微信小程序；逻辑复用 shared-core；TBD-1 已拍板〔CR-10〕 |
| 后端 | NestJS + TypeScript | 与前端同语言，AI 生成上下文统一；模块化 + 依赖注入天然适配纵切 |
| ORM/DB | Prisma + PostgreSQL 16 | 类型安全迁移；JSONB 承载动态字段；单库够用，避免过早分布式 |
| 缓存/锁 | Redis 7 | 权限缓存/分布式锁（Redlock）/幂等键去重〔业务延时触发归 RabbitMQ 延迟消息，DEC-1〕 |
| 消息队列 | **RabbitMQ**〔CR-01〕 | DLQ/延迟消息/灵活路由；Outbox event_store 仍为唯一事实源，MQ 仅作投递传送带 |
| 事件 | **Outbox 同库事件表（event_store）为事实源 + RabbitMQ 投递**〔CR-01〕 | 业务与事件同事务原子写入；提交后 dispatcher 读表投递，消费端 event_id 幂等 |
| 部署 | 2 台云服务器 Docker Compose | app×2 + pg + redis + nginx；每日全量备份 + WAL 归档 |
| 可观测 | 结构化日志 + Sentry + uptime 告警 | 双端 + 后端错误追踪 |
| AI 网关 | 统一代理层，模型可切换 | 生产涉客户数据走脱敏，预留国内模型切换（合规） |

### 1.2 UI 选型

**Web = HeroUI Pro（CollectUI）+ HeroUI OSS**〔CR-12〕：基于 React 19 + Tailwind CSS 4 重建 PC Web 设计体系；旧 Ant Design Pro 组件和 `packages/ui-web` 已整体移除。列表/详情仍须经 P7-2/P7-3 统一组件入口，禁止每页手搓；图表继续用 ECharts。

**内部移动端 = 企业微信工作台 H5（Taro + NutUI-React）**〔CR-11〕：内嵌企微工作台，企微 OAuth 免密登录（账号密码为根 + 企微 userid 绑定）。企微应用消息深链→路由表。接单/拨号/今日待办为高频路径优先优化。原生 App（RN + react-navigation）方案已废弃。

**外部提交端 = Taro 极简单页**：外部提交者 30 秒完成，无需登录复杂流程，判重反馈延迟标记（TBD-2）。技术栈用 Taro（一套代码出 H5 + 微信小程序，TBD-1 已拍板〔CR-10〕），UI 用 Taro 组件体系 + NutUI-React，逻辑走 shared-core。

设计语言与视觉规范另见前端设计约定（可参考 frontend-design 实践），此处只定选型与骨架。

### 1.3 关键 ADR 摘要（详见总纲 2.1）

ADR-001 三端 + shared-core；ADR-002 NestJS 模块化单体 + **〔CR-01〕Outbox 同库事件表 + RabbitMQ 投递**；ADR-003 PG 单库 + Redis + **〔CR-01〕RabbitMQ** + 金额整数分 + 快照/事件历史；ADR-004 L3 配置深度；ADR-005 平台七组底座；ADR-006 架构宪法最高约束；ADR-007 硬切换 + 影子周；ADR-008 集成网关 + 支付流水解耦。

## 第 2 章 系统架构设计

### 2.1 分层架构

```
┌──────────────────────────────────────────────────────────┐
│  端层   Web(Ant Pro)   内部移动端(企微H5·Taro)   外部端(小程序+H5·Taro)  │
└───────────────────────┬──────────────────────────────────┘
                        │ 只写视图，逻辑下沉
┌───────────────────────▼──────────────────────────────────┐
│  shared-core   API client(OpenAPI生成) / 类型 / Zustand /   │
│                业务hooks / 权限判断 / zod校验（single source）│
└───────────────────────┬──────────────────────────────────┘
                        │ REST /api/v1  (幂等键 X-Request-Id)
┌───────────────────────▼──────────────────────────────────┐
│  server (NestJS 模块化单体)                                  │
│  ┌────────────── platform 平台七组（P1~P7）──────────────┐  │
│  │ auth org permission ownership dedup task approval     │  │
│  │ scheduler notify alert dict config audit timeline     │  │
│  │ import-export attachment event-bus metrics integration│  │
│  │ ai-gateway                                            │  │
│  └───────────────────────────────────────────────────────┘  │
│  ┌────────────── modules 业务（M1~M13）──────────────────┐  │
│  │ 只调用 platform，模块间只走事件（event_store）          │  │
│  └───────────────────────────────────────────────────────┘  │
└───────────────────────┬──────────────────────────────────┘
                        │
        ┌───────────────┼────────────────┬─────────────────┐
   ┌────▼────┐    ┌─────▼─────┐    ┌──────▼──────┐   ┌─────▼─────┐
   │PostgreSQL│    │  Redis    │    │  RabbitMQ   │   │ 集成网关   │
   │单库+JSONB│    │缓存/锁/延时 │    │DLQ/延迟/路由 │   │支付/短信/企微│
   │event_store│   │(Redlock)  │    │(投递传送带) │   │/AI(脱敏)   │
   └─────────┘    └───────────┘    └─────────────┘   └───────────┘
```

### 2.2 依赖方向（架构生命线）

```
端  ──►  shared-core  ──►  server API
                              │
        platform  ◄────调用──  modules
            │                    │
            └──✗ 禁止 ────────────┘   platform 不 import modules
                    modules mX ✗──✗ modules mY   模块间不互 import，只走事件
```

三条边界铁律由 ESLint boundary 规则强制，CI 拦截违规合入：
1. `platform/**` 不 import `modules/**`
2. `modules/mX` 不 import `modules/mY`（跨模块只走事件或 platform 服务）
3. 跨模块只存 ID，禁止跨模块外键 JOIN 写业务逻辑（聚合在 M13/BFF 层）

### 2.3 事件驱动数据流（以"财务确认订单"为例）

```
M9 财务确认 ──写事务──► order.finance.confirmed 落 event_store（同事务）
                              │ 提交后 dispatcher 投递
        ┌─────────────┬───────┼────────────┬──────────────┐
     M2 建学员Identity  M7分班待办  调度→7日退款期计时  M6佣金台账冻结  M13成交计数
```

单一事件多订阅方互不阻塞，消费端自管位点 + 幂等（event_id 去重）。这是 AP-21 的落地：任何模块不得绕过事件直接读其他模块的表做统计。

### 2.4 部署拓扑与容灾

2 台云服务器 + Docker Compose（app×2 负载均衡 + pg + redis + nginx）。PG 每日全量 + WAL 归档，恢复演练在影子周前做一次。发布：main 合入自动部署 staging；prod 手动触发 + 发版清单（迁移脚本核对、config_param 新增核对、事件契约版本核对）。回滚：镜像回滚 + 迁移可逆（不可逆变更分两步发）。

## 第 3 章 模块设计

### 3.1 "人"的双侧对称建模

```
员工侧                          客户侧
Account   登录凭证              Person    自然人主档案（判重锚点）
Employee  人事档案              Identity  业务身份（客资/客户/学员/外部提交者…一人多身份）
Assignment业务任职×范围×区间     Ownership 归属×负责人×区间×变更原因
```

关键：业绩/服务归属按**成交/事件时点**的 Assignment/Ownership 判定，不看当前部门（AP-06）。转班/换人/离职 = 关旧区间开新区间，不删不改。归属读写只经 OwnershipService。

### 3.2 平台七组职责边界（详见总纲 2.2）

P1 身份组织（含 RBAC + 数据范围 + 脱敏 + 多身份 + **〔CR-11〕第三方登录绑定：账号密码为根，企微 OAuth / 微信 code2session 绑定入口**）、P2 流程任务（状态机 + 审批流 + 任务中心 + 调度规则 + 通用工单 + 工作日历）、P3 消息触达（通知 + 预警 + 公告；**〔CR-11〕通知生成与外部推送分离，外部推送经集成网关：内部 `WecomPushService` 推企微应用消息、外部只做站内**）、P4 数据配置（字典 + 参数中心 + 判重 + 归属 + 编号）、P5 留痕安全（审计 + 时间线 + 导入导出 + 附件）、P6 统计集成（事件总线 + 指标快照 + 排名 + 集成网关 + AI 网关）、P7 前端框架（动态路由 + 统一列表/详情 + 待办组件 + **〔CR-11〕移动端（企微 H5/小程序，Taro）规范**）。

**业务模块只调用平台，不自建**：待办不自建（用 P2-3 任务中心的角色视图）、通知不自建、归属不自写、状态不直改。

### 3.3 模块内标准结构（NestJS）

```
modules/m6-order/
  order.controller.ts     REST 端点（装饰器→OpenAPI）
  order.service.ts        业务编排（调 platform：StateMachine/Ownership/Event）
  order.repository.ts     数据访问（Prisma）
  order.events.ts         发布/订阅事件定义（对照契约表）
  dto/                    请求响应 DTO（zod schema 来自 shared-core）
  order.spec.ts           单测（红类 ≥90%）
```

### 3.4 状态机集中定义（以订单为例）

```
草稿 → 待报名审核 → 驳回待补正 → 待财务审核 → 财务驳回
                                    │
                              已确认(履约中) → 履约完成
                                    │
                              退款中 → 已退款 → 已关闭
```

所有流转唯一入口 `StateMachineService.transition(object, from, to, actor, reason)`：校验合法流转表 → 终态保护（已退款/已关闭禁回退）→ 写 timeline → 发事件。业务代码直接 update status = 打回。

## 第 4 章 数据设计规范

命名：表 snake_case 单数；金额 `*_cents bigint`（整数分，禁浮点）；时间 `*_at timestamptz`；枚举用 varchar + 字典校验（便于 L2 扩展），核心状态机枚举例外用 pg enum（防脏值）。软删除 `deleted_at`。统一审计字段由 Prisma 中间件自动填充；关键表变更自动写 audit_log。敏感列（phone/id_card）应用层加密 + 另存 hash 列做等值查询与判重。

事件表 event_store 骨架：`event_id / event_type / biz_ref_type / biz_ref_id / occurred_at / actor_id / payload(jsonb) / config_version`。配置变更留痕带版本，业务快照记当时生效的 config_version（佣金按成交时规则算，不按今天规则算，AP-20）。

迁移：Prisma Migrate；**迁移脚本禁止 AI 直接生成后合入，人工评审必过**；不可逆变更分两步发。

## 第 5 章 AI 生成代码的可持续可维护性规则

> 本章是"用 AI 全量编码"最关键的护栏。目标：让 AI 的产能转化为可维护、可审计、可演进的工程资产，而非技术债黑箱。

### 5.1 五条可维护性支柱

**支柱 1 — 结构可预测**。所有代码遵循固定目录与模块结构（第 3.3 节），AI 生成物落在预期位置，人和其他 Agent 能一眼定位。禁止 AI 自创目录结构或技术层横切。

**支柱 2 — 边界可强制**。依赖边界不靠自觉，靠 ESLint boundary + CI 拦截。AI 再"聪明"也无法绕过跨模块 import 的机器检查。这是防止 AI 悄悄制造耦合的根本手段。

**支柱 3 — 契约可校验**。接口以 OpenAPI 自动生成类型（编译期发现变更），事件以契约表为准，表单校验 zod single source。AI 编造的接口/字段会在编译或契约比对时暴露。

**支柱 4 — 红线可复核**。金额/归属/状态机/权限/审批/迁移/定时任务分级为红类，测试先行 + 逐行人读。AI 在这些点的错误代价最高，必须人兜底。

**支柱 5 — 变更可追溯**。跨模块改动先开工单，规则变更走 M11，受控文档版本递增 + changelog。任何 AI 产出都能回溯到"为什么改、谁批的"。

### 5.2 代码可读性与一致性约定

统一风格（Prettier + ESLint 强制，AI 产出一律格式化）；命名遵循规范（表/字段/事件/错误码命名约定见 CLAUDE.md）；每个红类函数必须有说明其业务规则来源的注释（如 `// BR-C04 7日退款期内佣金冻结`），让规则与代码双向可查；禁止魔法数字，业务参数一律引用 config_param 键（如 `lead.accept.timeout`），不写死数值（AP-20）。

### 5.3 AI 产出的防腐层

**防幻觉**：接口以 OpenAPI 生成类型为准，事件以契约表为准，规则以总纲 BR/MT 为准；AI 遇到缺失一律标 TBD 停推，不自行发明。

**防耦合**：边界 ESLint 规则 + 审查员 platform/modules import 检查。

**防不一致**：shared-core 是逻辑唯一源，端上只写视图；同一 zod schema 前后端共用。

**防隐藏 mock**：mock 必须标 `// MOCK-TODO(工单号)`，CI 每周报告清单，联调用 staging 真实接口。

**防脏历史**：历史依赖快照/事件，禁止用当前配置/人员反推过去。

### 5.4 AI 自审与人复核闭环

每个模块完成后，实现者 Agent 把宪法 AP-01~21 作为检查清单对自己的 diff 逐条自查输出报告；审查员 Agent 独立对照打勾（不同模型实例）；找 bug 员对抗测试；红类由人逐行放行。四道闸叠加，见《AI多Agent协作机制》第 4 章。

### 5.5 技术债管理

`MOCK-TODO`、`FIXME(工单号)`、红类未达覆盖率的点，全部登记为 M11 工单，每周范围审查会过一遍。围栏期（08-18 起）只修不加，未清技术债进 4.0 池。禁止"先上线再说"的无记录妥协。

### 5.6 可维护性验收清单（每模块合入前）

```
[ ] 目录结构符合第 3.3 节，无自创横切层
[ ] boundary ESLint 全绿（无跨模块 import）
[ ] 接口有 OpenAPI，shared-core 类型已同步
[ ] 红类函数有规则来源注释，无魔法数字（引 config_param）
[ ] 红类单测 ≥90%，含边界/并发/时区/幂等
[ ] 无未登记 mock（MOCK-TODO 均有工单号）
[ ] AI 自审报告 + 审查员打勾表齐全
[ ] 跨模块改动有 M11 工单号
```
