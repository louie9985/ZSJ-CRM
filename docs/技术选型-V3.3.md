## 2. 技术选型定稿（结论 · 理由 · 否决项）

### 2.1 基础设施与运行时

| 项 | 结论 |
|---|---|
| 云 / 系统 / 部署 | 腾讯云 · Ubuntu · Docker Compose（**2 台 app + pg + redis + nginx**，对齐总纲 8.1） |

**否决项**：
- **antd-mobile（RN 版）**：Web/Mobile 已决定视觉解耦，一致性不再是理由；且 RN 版维护活跃度弱。

### 2.3 鉴权（红类核心，AP-01/02/03/14）

**认证（你是谁）**
- **JWT access（短命）+ Redis refresh（可失效，用于踢人/收权）+ 权限不进 token 靠现算**。
- 本质 = DRF `djangorestframework-simplejwt` 双 token 模式平移到 NestJS（`@nestjs/jwt`）+ Redis（refresh 存 Redis 而非 DB，失效更快，且顺带权限缓存）。
- **否决纯 JWT**：权限/任职会变动，纯 JWT 难即时收权。

**授权·身份（AP-01 四层分离 + 融合方案）**
- 账号 / 操作人 / 员工档案 / 业务任职分开；JWT 只放稳定锚点 `account_id` / `operator_id` + token 版本；任职/权限/数据范围全部**现算**，不进 token。
- **多任职融合方案**：每人有「当前活动任职」，默认=主任职（单任职者无感）；多任职者可**显式切换**身份，一次一个，**不做权限并集**。切换服务端校验合法性（AP-03）、写审计；业务归属/审计记「操作时活动任职**快照**」（AP-06/08/12）。
- 参考标杆：AWS IAM Assume Role、钉钉主部门、Salesforce 角色层级。

**授权·功能权限（你能做什么）**
- **RBAC**：权限点（如 `customer:delete`）→ 角色 → 任职；`/me/permissions` 返回当前身份权限点集合；前端控显隐，**后端每个写操作仍校验**（AP-03）。

**授权·数据范围（AP-02，你能作用在哪些数据）**
- 四档 `scope_type`：`SELF`（仅本人）/ `ORG_SUBTREE`（本组织及下级，主模型，顺组织树卷）/ `CUSTOM`（特例：指定额外组织/数据域）/ `ALL`（老板/顶级管理员跨全树）。
- 老板「看全部」用显式 `ALL` 标记，**不靠**挂到组织树顶端实现。
- 即便 `ALL`，敏感字段（手机号等）仍走 **AP-14 单独鉴权 + 访问审计**。
- **否决 record-level（逐记录规则）④**：CRM 用不上，过度设计。

**叠加层·临时授权（Just-In-Time Access）**
- 可临时获取超范围权限，**但必须经审批**：申请→审批→带 **TTL** 授予→到期自动回收（定时任务扫描，AP-11），全程审计（AP-12）、事件驱动（AP-21）。作为**独立业务模块**单独设计，不混进基础鉴权。

### 2.4 周边服务

| 项 | 结论 | 关键点 |
|---|---|---|
| **文件存储** | 生产**腾讯云 COS**（预签名直传 + 后端管状态/下载鉴权）；本地开发**本地文件系统驱动** | platform 层 `StorageService` 抽象，`STORAGE_DRIVER` 切换。落 AP-13 四要素。**已知代价**：本地不走真实预签名链路，需预发/联调覆盖。否决本地 MinIO（用户选省事） |

| **审计日志** | 独立 `audit_log` 表，**入库、只增不改不删** | 产生方式：**事件消费者为主（订阅 RabbitMQ 事件自动生成）+ 敏感访问等无事件场景单独埋点**。字段含操作人、**活动任职快照**、action、resource、before/after、result、trace_id、ip、时间 |

## 3. 重点决策详述：消息队列（CR-01，🔴 根本性变更）

总纲 ADR-002 明确「**不上 MQ**，模块间事件驱动用**同库事件表**」，8.1 用 BullMQ 做延时/倒计时。本提案推翻此决策，改用 RabbitMQ。以下**公正列出双方**，供 M11 裁决。

### 3.1 总纲原方案（同库事件表，不上 MQ）的优点 — 不应忽视

- **少运维一个组件**：event_store 表本身就是事件总线，dispatcher 轮询即可投递，无需部署/监控 RabbitMQ。
- **强一致天然**：事件与业务同库同事务，Outbox 语义直接成立，不存在「写库成功、投 MQ 失败」的窗口。
- **契合现阶段规模**：模块化单体、单进程，同库事件表足以支撑；BullMQ（基于反正要装的 Redis）已能覆盖延时/倒计时。
- **符合宪法「简单优先」气质**：不为不存在的需求付运维税。

### 3.2 RabbitMQ 方案的优点 — 用户选择的依据

- **长期天花板高**：原生 DLQ（死信队列）、延迟消息、灵活路由，随通知去重（AP-10）/重试（AP-11）复杂化更从容。
- **基础设施一步到位**：MQ 属基础设施，后期更换成本高；用户明确取「现在用不到不代表以后用不到」的长期主义。
- **迁移安全性有保障**：无论 MQ 选谁，事件链路都是 `event_store（唯一事实源）→ dispatcher → MQ → 消费端幂等`。**MQ 只是传送带，event_store 才是事实源**；即便未来换 MQ，事件正确性不受影响，风险可控。

### 3.3 结论与实施口径

- **采用 RabbitMQ**（用户拍板，长期主义）。
- **但保留 Outbox 内核**：严禁「先写库再丢 MQ」的天真做法。事务内写 event_store，提交后 dispatcher 读表投递 RabbitMQ，消费端按 `event_id` 幂等去重。**这条恰好让 ADR-002 的「同库事件表」精神以另一种形式延续**——事件表没被丢弃，只是多了 RabbitMQ 做投递加速与高级路由。
- **待回写**：ADR-002 表述改为「模块间事件驱动；Outbox 同库事件表为事实源 + RabbitMQ 投递」；8.1 的 BullMQ 相应调整。

## 4. 事件链路架构（贯穿 AP-21，不随 MQ 选型改变）

```
业务动作
  └─(同一DB事务)→ 记业务数据 + 写 event_store        ← 唯一事实源
                        │ commit
                        ▼
                   dispatcher（读未投递事件）
                        │
                        ▼
                   RabbitMQ（传送带 / 路由 / DLQ / 延迟）
                        ├→ 审计消费者      → audit_log（#9）
                        ├→ 通知消费者      → 站内通知(必生成,事实源) + 外部推送(企微应用消息,best-effort)（#10）
                        ├→ 待办消费者      → 生成待办
                        └→ 指标消费者      → 报表/快照
```

**铁律**：指标/通知/待办/审计/实时推送**全是 event_store 的消费者**，无一绕过事件直读表（AP-21）。消费端一律按 `event_id` 幂等。

## 6. 重点决策详述：移动端推送（CR-06 / R-1，深入设计 2026-07-07）

> 🚫 **本章已被 CR-11（2026-07-08）整章作废。** 原生 App 废弃后无极光 JPush / Expo / APNs+FCM。内部移动端改企微 H5，推送改**企业微信应用消息**，外部只做站内通知。本章全文保留仅作决策留痕，**不再作为实施依据**，当前生效口径见第 9 章。

### 6.1 问题

Expo 内置 Push 底层走 FCM，FCM 依赖 Google Play Services；国内出厂安卓普遍无 GMS，部分品牌因授权无法自装 → **纯 Expo Push 在国内安卓推不到**。国内安卓是本项目主力机型，此路不通。

### 6.2 结论：统一极光 JPush（否决双轨）

- **一套 SDK 统管全通道**：极光官方 RN 插件（`jpush-react-native`）聚合 **APNs（iOS）+ FCM（海外安卓）+ 华为/小米/OPPO/VIVO/魅族等厂商系统级通道（国内安卓）**。
- **否决「iOS Expo Push + 安卓极光」双轨**：极光已能多路复用，双轨是多余复杂度。
- 相当于**回归总纲 8.1 原选的极光/个推**——总纲此项本就正确，本提案确认沿用（选极光，因其 RN 插件官方维护、资料更全）。

### 6.3 代价：Expo 形态从「纯托管」升级为「prebuild + dev client」

原生 SDK 不能用于 Expo Go 托管工作流，因此：

| 维度 | 纯托管 Expo Go | **本项目采用：Prebuild + Dev Client** |
|---|---|---|
| 预览 | Expo Go 扫码 | EAS 打自定义 **dev client** 装机 |
| 原生模块 | 仅内置 | **可集成极光等任意原生 SDK**（config plugin） |
| 打包 | — | **EAS Build** |

**关键澄清**：这**不是放弃 Expo**。仍享有 Expo Router / EAS / OTA 热更新 / `expo install`，只是不能用最简的 Expo Go 扫码预览。**gluestack v5 + NativeWind + Lucide + FlashList 的 UI 决策完全不受影响。**

### 6.4 实施要点

1. 推送 SDK：`jpush-react-native`，config plugin 集成，EAS Build 出包。
2. **Android 通知渠道**：Android 8.0+ 必须建 notification channel，否则通知不显示——必做项。
3. **与事件架构对接**：后端「通知消费者」订阅 RabbitMQ 事件 → 调**极光服务端 API** 推送；在线用户走轮询可拉、离线靠极光推到通知栏。极光只做「最后一公里投递」，事实源仍是 event_store（AP-21）。
4. iOS 需 APNs 证书；各安卓厂商通道需在极光后台配置对应厂商应用参数（华为/小米等各自注册）。

## 7. 重点决策详述：权限数据模型（深入设计 2026-07-07，针对 PRD-B1）

**核心结论：不另起炉灶。** PRD-B1 已定义身份/组织/权限的绝大部分表，本设计**80% 复用既有表**，只做「一处档位调整 + 三处补表」。

### 7.1 直接复用 PRD-B1 既有表（无变更）

| 决策 | 复用的 PRD-B1 表 | 对齐宪法 |
|---|---|---|
| 四层身份分离 | `account` / `employee` / `assignment` | AP-01 |
| 任职带组织范围 + 历史快照 | `assignment`（`scope_type/scope_id` + `start_at/end_at` 时间区间判定） | AP-01/06 |
| 组织树 | `department`（`parent_id` + **`path` 物化路径**） | — |
| 功能权限 RBAC | `role_permission`（role_code → menu/button/api 三级） | AP-02 |
| 审计 | `audit_log`（actor/action/resource/before-after/ip） | AP-12 |
| 审批链（临时授权复用） | `approval_flow_def` / `approval_instance` / `approval_record` | — |

### 7.2 CR-08：调整 `role_data_scope.scope` 档位

- **原**：`self / group / dept / all`
- **新**：`SELF / ORG_SUBTREE / CUSTOM / ALL`
- **理由**：PRD-B1 已有 `department.path` 物化路径，用 `ORG_SUBTREE` + path 前缀匹配即可统一表达「本节点及所有下级」，无论组/部门，比硬编码 group/dept 两档更优雅；并新增 `CUSTOM`（特例额外数据域）与既有 `ALL`（老板/顶管跨全树）。
- **口径不变**：查询层拦截器统一注入 scope 条件，业务代码禁止手写（AP-02）。即便 `ALL`，敏感字段仍走 AP-14 单独鉴权 + 访问审计。

### 7.3 CR-09：新增三处（PRD-B1 未覆盖）

**① `data_scope_grant`（CUSTOM 额外数据域授权，长期/特例）**
解决 `role_data_scope` 只能按角色配、无法表达「某人额外能看某区域」的缺口。
```
data_scope_grant
  id
  assignment_id     授给「任职身份」而非「人」（与身份融合方案一致）
  resource          lead / order / student / ...
  scope_type        org_subtree / specific
  scope_ref         department_id 或具体数据域 id
  granted_by, reason
  start_at, end_at  支持永久或带期限
  + 统一审计字段
```

**② `temp_access_request`（临时授权 JIT，必经审批 + TTL）**
与 ① 的区别：**必须走审批、有明确到期、到期自动回收**。
```
temp_access_request
  id
  requester_assignment_id
  resource, scope_ref            要临时访问什么
  reason
  approval_instance_id           复用 PRD-B1 既有审批链
  status                         pending/approved/rejected/expired/revoked
  granted_at, expires_at         TTL；到期由定时任务扫描回收（AP-11）
  revoked_at, revoked_by
  + 统一审计字段
```
申请→批准→使用→回收全程写 `audit_log`（AP-12）、发事件（AP-21）。作为独立业务模块，一期可「只建模型、暂缓完整实现」（视排期）。

**③ `session` 补 `active_assignment_id`（当前活动任职）**
PRD-B1 已提及 `session`（多端会话），补一个字段承载「当前以哪个任职身份工作」。
```
session（补字段）
  ...既有字段
  active_assignment_id   多任职切换用；不进 JWT，存服务端会话（与「权限现算」一致）
```
- 单任职者：登录自动设为唯一 assignment，无感。
- 多任职者：切换身份 = 更新此字段，**服务端校验该 assignment 属于本人且生效**（AP-03），并写审计。
- 每次请求按 `active_assignment_id` 现算功能权限 + 数据范围。

### 7.4 权限求值流程（运行时）

```
请求进来（JWT 验签 → account_id/operator_id）
  → 取 session.active_assignment_id（当前身份）
  → 功能权限：role_permission[assignment.role_code]（Redis 缓存）→ 判 api/button
  → 数据范围：role_data_scope[role_code][resource] 得基础档位
             + data_scope_grant（叠加 CUSTOM）
             + temp_access_request（叠加未过期的临时授权）
  → 查询层拦截器按最终 scope 注入过滤条件（AP-02，业务代码不手写）
  → 敏感字段访问再过 AP-14 单独鉴权 + 写访问审计
```

## 8. 重点决策详述：外部提交端技术栈（CR-10，🟡 拍板 TBD-1，2026-07-07）

### 8.1 背景

总纲 TBD-1 挂了两问：①外部端形态（独立端 vs 并入员工App）；②若独立，技术栈用「React 同 web 栈裁剪」还是「Taro（为小程序预留）」。形态一问早已默认"独立"（1000 兼职装 App 转化损耗大）；技术栈一问此前留默认「React 裁剪」、Taro 仅作"若后续要小程序"的备选。

### 8.2 结论：采用 Taro

- **一套代码出 H5 + 微信小程序**：外部兼职/轻创提交场景，微信内点开即用是主路径，小程序入口天然契合。Taro 编译期多端输出，等于把 TBD-1 里"若后续要小程序"的触发条件一次性满足。
- **逻辑照旧下沉 shared-core**：与 ADR-001「功能一致由 shared-core 保证」不冲突——共享的是逻辑/校验/类型，Taro 只接管 `h5-partner` 的 UI 与编译工具链。
- **UI 组件体系**：Taro 官方组件 + NutUI-React（京东系，Taro 生态活跃）承载 30 秒极简表单，无需 Ant Design Pro 那套中后台重组件。

### 8.3 已接受代价

- **放弃复用 Web 的 Ant Design Pro**：`h5-partner` UI 层不再直接裁剪 Web 组件，改用 Taro 组件体系；但外部端本就极简（单页提交），重组件复用价值低，代价可接受。
- **工具链差异**：Taro 用自有编译器（非 Web 的 Vite），monorepo 内 `h5-partner` 构建脚本独立；shared-core 需保证对 Taro 运行时的兼容（纯逻辑/zod/API client 无 DOM 依赖，天然可用）。
- **小程序合规**：若正式上线微信小程序，需注册小程序主体、走微信审核；一期可先只出 H5，小程序作为已打开的能力按需启用。

## 9. 重点决策详述：移动端由 App 改小程序/H5（CR-11，🔴 推翻 CR-02/06，2026-07-08）

### 9.1 背景与推翻理由

会议评估后确认**原生 App 不合适**，废弃 CR-02（Expo+gluestack 原生 App 栈）与 CR-06（极光 JPush 推送）。按**使用者**重划移动端格局：

| 端 | 使用者 | 形态 | 栈 |
|---|---|---|---|
| PC Web（packages/web） | 内部员工（桌面） | **HeroUI Pro（CollectUI）+ HeroUI OSS** | **React 19 + Tailwind CSS 4** |
| 内部移动端（packages/mobile，沿用命名） | 内部员工（销售/新媒体等） | **内嵌企业微信工作台的 H5** | **Taro** |
| 外部提交端（packages/h5-partner） | 外部兼职 | 微信小程序 + H5（保留双输出） | **Taro** |

原 `packages/mobile` 的 RN App 职责由「企微 H5」接管，命名沿用 mobile。

### 9.2 改小程序/H5 同时解掉两个痛点

- **抢单可靠推送有救**：内部端放进企业微信，可用**企微应用消息**做组织内可靠触达（叫得醒用户），远强于小程序订阅消息。
- **「功能对齐 Web」可行**：内部端是 H5，**无包体积上限**、性能远好于小程序，13 模块功能镜像现实可行（小程序 2MB 主包顾虑作废）。

### 9.3 统一技术栈（内外两个移动端一致）

- 框架：**Taro + React**（内部端也用 Taro，与外部统一工程体系、最大化 shared-core 复用、只维护一种框架）
- 组件层：**NutUI-React**（取代 gluestack-ui v5，H5+小程序双端都跑）
- 样式：**Tailwind token**（主色/圆角/间距/字号阶，移动端设计系统单一源；小程序侧 weapp-tailwindcss 落地）
- 图标：**Lucide**（与 Web 共用，小程序内 SVG 用）
- 用户此前保留的组件方向口径（Tailwind token / Lucide / 列表虚拟化意图）100% 平移；FlashList 具体库废弃，改 Taro 虚拟列表。

### 9.4 登录：账号密码为根 + 第三方绑定快进

- **账号密码 = 唯一根身份**，任何端可直接登录，不依赖任何绑定（兜底主路径）。
- 企微 userid（内部）/ 微信 openid（外部）= 可选绑定的快捷入口，挂在「账号」层，契合 AP-01。
- 新增**第三方绑定表**（`account_id ↔ provider ↔ external_id`），约束**一账号至多绑一个第三方**（内部只在企微、外部只在微信，无交叉）。
- **首次触达**：企微/微信里首次打开 → 弹授权拿 external_id → 查绑定 → 没绑则引导账号密码登录一次完成绑定 → 之后免密快进。
- 登录入口：内部**企微 OAuth**、外部**微信 code2session**，拿 external_id 后并入既有 JWT+Redis 体系。

### 9.5 通知/触达：生成与推送分离（改 AP-10）

- **一个事实源，多个通道**：业务事件 → ①站内通知（**永远生成、可靠、是事实源**，写站内通知表+红点）→ ②外部推送（叫醒用户、**分端 best-effort、增强层**）。推送失败不影响通知已生成。
- 站内：**轮询起步**（不上 WebSocket），红点/未读；抢单轮询刷池 + 乐观锁口径不变。
- 内部推送：platform 层新增 **`WecomPushService`**（消费通知事件调企微 API 推应用消息带 H5 深链；幂等 event_id 去重）。**纳入架构口径、实现可后置**。
- 外部推送：**只做站内、砍掉微信订阅消息**（极简提交场景推送价值低）。
- **AP-10 补充约束**：通知的「生成」与「外部推送」分离；生成必然发生（站内事实源），外部推送按端能力（企微=可靠，外部只站内）；收件人触达通道由身份绑定决定。
- 废弃：极光 JPush / Expo Push / APNs+FCM / notification channel 整套。

### 9.6 已接受代价

- 企微 H5 交互「原生味」弱于 App（无法用原生手势/离线能力），但内部办公场景可接受。
- 外部无主动推送，用户靠下次打开消化站内通知——外部本为低频提交，可接受。
- 企微应用消息依赖账号已绑企微 userid，未绑成员只能靠站内。
