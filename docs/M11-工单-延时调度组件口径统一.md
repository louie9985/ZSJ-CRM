## 1. 问题：四处文档口径漂移

「2 分钟接单 / 10 分钟首触 / 7 日佣金解冻」这类**一次性业务倒计时**，到底由哪个组件承载延时触发，现行文档说法不一：

| 文档 | 位置 | 表述 | 归属组件 |
|---|---|---|---|
| 技术选型-V3.2 | §2.1 缓存/锁行 | Redis：权限缓存、幂等键、分布式锁、**延时队列** | **Redis** |
| 总纲-V3.2 | ADR-003 | Redis（倒计时/分布式锁/**延时队列**） | **Redis** |
| PRD-B1-V3.3 | §P2-4 调度引擎 | **RabbitMQ 延时/延迟消息**（2分钟/10分钟/7日）+ 每分钟周期扫描 | **RabbitMQ** |
| 开发文档-架构 | §1.1 技术栈表 | RabbitMQ：DLQ/**延迟消息**/灵活路由 | **RabbitMQ** |
| 开发手册细则-V3.1 | §2.3 定时任务〔本次刚回写 CR-01〕 | RabbitMQ 延迟消息触发 + Redis 分布式锁 | **RabbitMQ** |

**非硬冲突**（Redis、RabbitMQ 都保留了延时用途），但**同一业务倒计时没有唯一实现口径**——B1 实现调度引擎（P2-4）时不同开发/AI 会各写各的，导致同类倒计时两套实现，违背单一源精神。

**已澄清、不在争议内的部分**（PRD-B1 §P2-4 已区分）：
- **周期性扫描**（90 日公海、考前 N 天）：cron 式每分钟扫描 + 幂等（以业务状态为准，非以调度记录为准，AP-11）——此项无歧义。
- **分布式锁**：Redis——无歧义。
- 争议**仅在「一次性延时触发」**用 Redis 还是 RabbitMQ。

| **DEC-1** ✅**已定** | 一次性业务倒计时（2分钟/10分钟/7日）的延时触发组件 | (a) **统一 RabbitMQ 延迟消息**（delayed-message 插件或 TTL+DLX）；Redis 退出延时职责，只保留缓存/分布式锁/幂等键<br>(b) **统一 Redis 延时队列**（ZSET 到期轮询）；RabbitMQ 只做事件投递/路由/DLQ，不承延时<br>(c) 分工：短延时（≤分钟级、要精度）用一种，长周期（7日）用另一种 | **✅ 定 (a)**（2026-07-08）——见 §3 |

## 3. 建议方案理由（(a) 统一 RabbitMQ 延迟消息）

- **顺 CR-01 的长期主义**：CR-01 上 RabbitMQ 的核心理由就是「原生 DLQ / 延迟消息 / 灵活路由，随通知去重/重试复杂化更从容」。既已引入，延时触发正是它的主场，不必再让 Redis 兼一份延时职责。
- **组件职责单一、好维护**：Redis 专注缓存 + 分布式锁 + 幂等键去重；RabbitMQ 专注事件投递 + 延时 + DLQ。一种延时机制一处实现，消除「两套倒计时」。
- **与事件链路同源**：延时触发本质是「到点投递一条延时事件 → 消费端处理」，天然复用 event_store → dispatcher → RabbitMQ → 消费端幂等（AP-21）的既有链路，无需另起 Redis 轮询 worker。
- **代价**：需启用 RabbitMQ `rabbitmq-delayed-message-exchange` 插件（或 TTL+死信队列方案），运维上多一个插件依赖——但 RabbitMQ 已在基础设施内，增量成本低。
- **反方（选 (b) 的理由，供权衡）**：Redis ZSET 延时更轻、无需插件，倒计时精度足够；若认为 RabbitMQ 延迟插件运维不确定性高，可选 (b)。但代价是 RabbitMQ 的延时能力闲置、Redis 又背一类队列职责。

> 无论选 (a) / (b)，**周期扫描 + Redis 分布式锁 + 幂等（以状态为准）** 三项不变；event_store 唯一事实源不变。

## 6. 建议：调度统一封装（无论 DEC-1 选哪个）

为防口径再漂移，建议 P2-4 提供**唯一入口** `SchedulerService.scheduleOnce(businessKey, delay, eventPayload)` / `SchedulerService.registerCron(...)`，内部封装选定组件，业务代码只调此服务、不直接碰 RabbitMQ/Redis 延时 API——与 `StateMachineService` / `OwnershipService` 同样的「唯一入口」纪律。此项不依赖 DEC-1 结果，建议一并采纳。
