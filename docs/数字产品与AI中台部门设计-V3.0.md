## 1. 部门总体定位与战略判断

> **核心判断** 数字产品与AI中台不是传统技术部，也不是普通开发部，而是公司从"人力驱动增长"升级为"系统、数据、AI驱动增长"的经营中台。

结合公司当前阶段，数字产品与AI中台短期主定位是内部数字化中台，中期升级为数字产品与AI中台，长期再拆分为内部系统中台、外部AI产品事业线、IT运维/数据安全。

当前第一优先级是AI-CRM系统上线，同时推动各部门AI赋能，最终实现内部管理全面AI化。第二大目标是学员AI题库系统，第三大目标是健康行业从业者客户管理工具。

这个部门的最大挑战不是技术本身，而是业务复杂度、需求优先级、接口集成、数据治理和团队能力结构之间的矛盾。现在团队只有3名以全栈开发为主的成员，产品、数据、项目管理和运维安全能力需要通过制度化机制补齐。

### 1.1 三个阶段的定位

| 阶段 | 部门定位 | 重点任务 | 不应承担的事项 |
|---|---|---|---|
| 短期：月营收300万以内 | 内部数字化开发小队 | AI-CRM主链路、核心部门页面、企微/小鹅通/金蝶基础打通、需求工单中心 | 不承担大量临时报表、不做非核心业务深度定制、不继续负责电脑采购和日常行政IT杂务 |
| 中期：月营收800万以内 | 数字产品与AI中台 | 核心业务AI助手、老板/主管大盘、数据口径、流程引擎、AI题库MVP | 不无限接收未审批需求、不做所有部门的人工数据统计员、不替业务部门做业务执行 |
| 规模期：月营收1600万以内 | 公司经营系统与AI产品中台 | 经营操作系统、外部AI产品试商业化、数据安全、AI治理、系统稳定性、自动化提效 | 不靠堆人解决需求混乱，不让8人团队背负所有外部产品完整商业化压力 |

## 2. 业务模式与对公司的业务贡献

数字产品与AI中台的业务模式不是"接需求写代码"，而是通过系统建设、AI工具、数据资产和外部产品孵化，持续放大公司各部门的人效和经营可控性。

### 2.1 四类业务贡献

| 贡献类型 | 具体表现 | 衡量方式 | 阶段性目标 |
|---|---|---|---|
| 内部提效 | 自动统计、自动提醒、自动归档、自动质检、自动对账、自动绩效 | 节省工时、减少岗位重复劳动、处理时效提升 | 保底3倍提效，冲刺30倍，战略场景追求300倍 |
| 业务增长 | 减少漏单、提升销售承接、提升学习规划师复购识别、提高客资转化 | 漏单率、成交率、复购率、订单处理效率、客户跟进完成率 | 让AI-CRM直接影响收入结果，而不是只记录数据 |
| 风险降低 | 防止错单、飞单、佣金错误、过度承诺、数据泄露、权限混乱 | 退款率、投诉率、异常订单、越权访问、导出审批、AI调用日志 | 把管理风险提前变成系统预警 |
| 产品收入 | AI题库、AI职业规划、健康从业者客户管理工具、知识库产品 | 活跃用户、并发人数、付费转化、留存、客户满意度 | 先内部验证，再小范围商业化，最后产品化销售 |

### 2.2 对公司增长模型的贡献

| 公司目标 | AI中台贡献方式 | 示例 |
|---|---|---|
| 月营收300万以内 | 把流程跑通，减少漏单和错单，建立数据基础 | 客资分配、销售今日待办、报名履约、学习规划师提醒、基础老板大盘 |
| 月营收800万以内 | 让管理从人工表格转为系统数据，开始用AI辅助岗位提效 | 自动绩效、AI销售助手、AI学习规划助手、财务对账、质控抽检 |
| 月营收1600万以内 | 让200人组织仍能被8人中台支撑，形成经营操作系统 | 经营大盘、利润分析、饱和度预警、数据安全、外部AI产品MVP |

### 2.3 业务价值公式

| 项目 | 说明 |
|---|---|
| 内部提效价值 | 节省工时 × 岗位人力成本 × 使用频率。 |
| 业务增长价值 | 转化率提升 × 有效客资数 × 客单价，或复购率提升 × 可复购客户池 × 复购客单价。 |
| 风险降低价值 | 减少退款金额 + 减少投诉处理成本 + 减少佣金错误 + 减少合规风险损失。 |
| 产品化价值 | 外部用户数 × 付费转化率 × 客单价 × 留存周期。 |
| 部门总价值 | 内部提效价值 + 业务增长价值 + 风险降低价值 + 产品化价值。 |

### 3.2 部门不应被拖入的低价值事项

- 不负责日常电脑采购、账号采购、行政资产管理，只提供技术建议和权限接口支持。
- 不替业务部门人工整理表格，除非该工作已经被定义为系统化/自动化需求。
- 不接受员工私聊插队需求，所有需求必须进入需求工单中心。
- 不为每个部门做无限个性化页面，第一版优先做共性流程、共性字段、共性大盘。
- 不为业务部门承担最终业务结果责任，AI中台负责系统工具和数据能力，业务部门负责使用与业务执行。

### 3.3 部门边界与协作关系

| 协作对象 | AI中台负责 | 业务/职能部门负责 |
|---|---|---|
| 老板 | 提供大盘、需求方案、风险提示、开发进度 | 确定重大优先级、业务规则、验收方向 |
| 新媒体 | 客资入口、账号数据、客资质量分析、结算状态 | 内容、客资初筛、账号运营、轻创陪跑执行 |
| 销售 | 分配、接单、跟进提醒、AI话术、业绩大盘 | 客户沟通、成交、跟进记录、承诺合规 |
| 报名履约 | 订单、合同、资料、开课、履约提醒 | 订单审核、合同办理、开课拉群、异常补正 |
| 学生服务 | 学习计划、服务待办、复购机会、AI学习建议 | 学员沟通、督学、职业种草、复购成交 |
| 财务 | 金蝶接口、对账台、佣金计算、毛利字段 | 收款确认、退款审核、税票处理、财务规则 |
| 人力 | 绩效数据、岗位饱和度、培训记录 | 绩效制度、招聘、员工管理、奖惩执行 |
| 质控 | 抽检工具、证据链、投诉流程、风险预警 | 质控判责、投诉处理、服务质量监督 |

## 4. 按营收阶段设置人员编制

> **编制原则** 数字产品与AI中台必须谨慎加人。公司不是靠扩大技术部来解决混乱，而是靠需求纪律、AI辅助开发、组件复用、业务部门自测、外部顾问补位，让小团队发挥高杠杆。

| 营收阶段 | 部门编制 | 核心组织形态 | 必须完成 | 不能贪多 |
|---|---|---|---|---|
| 月营收300万以内 | 3-4人 | 创业开发小队：老板兼产品负责人，技术负责人带2名全栈，必要时补1名产品/测试实施 | AI-CRM核心链路、Web/H5、企微/小鹅通/金蝶基础接口、需求工单中心、基础权限和日志 | 不做完整外部产品，不深做就业和IP产品研发，不做所有AI助手 |
| 月营收800万以内 | 5-6人 | 小型中台：补产品/业务分析、测试实施/数据，形成需求-开发-测试-培训闭环 | 核心业务全流程、老板/主管大盘、AI助手一期、绩效自动化、AI题库MVP | 不做复杂数据仓库，不做全量聊天智能分析，不做过度个性化页面 |
| 月营收1600万以内 | 8人 | 高杠杆中台：产品、开发、AI、数据、测试、运维安全齐备但仍保持克制 | 经营操作系统、部门饱和度、数据治理、AI治理、外部产品MVP、系统稳定性 | 不扩到大型研发中心，不同时开太多外部商业化产品线 |

### 4.1 为什么1600万以内仍建议8人

如果数字产品与AI中台扩编过快，会出现"研发团队变成成本中心"的风险。公司当前的核心竞争力仍是健康职业教育业务、内容获客、销售转化、学习规划复购和就业服务，不应过早把技术团队做成大型研发中心。

8人编制的前提是：第一，需求必须严格进入工单池；第二，业务部门必须承担验收和使用责任；第三，AI中台只做高复用、高价值、可沉淀的系统能力；第四，复杂法务、税务、安全、架构顾问可以外部采购，不必全部内建。

### 4.2 外部顾问与临时资源使用建议

| 资源类型 | 什么时候用 | 不建议内招的原因 |
|---|---|---|
| 云服务器/安全顾问 | 上线前架构审查、备份策略、安全加固、权限审计 | 阶段性专业需求，不必长期占编 |
| 企业微信/金蝶/小鹅通接口顾问 | 接口对接复杂或官方文档不清时 | 一次性集成经验比长期岗位更重要 |
| UI/交互顾问 | 第一版关键页面体验较差、员工使用阻力大时 | 不必一开始配置专职设计 |
| 法务/隐私合规顾问 | AI调用、个人信息、合同承诺、数据导出规则确认时 | 专业责任需要外部意见，不适合由开发拍板 |
| 高级架构评审 | 并发、权限、数据库、日志、备份、灾备方案定稿时 | 保证方向正确，避免早期架构债 |

## 5. 三阶段岗位设置与岗位职责

### 5.3 月营收1600万以内：8人高杠杆中台

## 10. 需求管理、项目管理与上线验收机制

### 10.1 标准需求流程

- 员工提出需求，必须说明问题、使用场景、希望结果、紧急程度。
- 部门主管审核，确认是否为部门真实需求，而不是个人临时想法。
- AI部门初评，判断属于Bug、优化、新功能、临时报表、数据导出或紧急需求。
- AI部门给出解决方案、影响范围、开发周期、上线风险。
- 老板审批重大需求；普通需求由AI部门负责人结合部门负责人意见排期。
- 进入开发、测试、验收、上线、培训、使用率追踪、复盘闭环。

### 10.2 需求类型与处理规则

| 需求类型 | 定义 | 处理规则 | 验收人 |
|---|---|---|---|
| Bug | 系统已有功能不能正常使用 | 进入Bug池，按严重程度处理；影响成交/收款/履约为高优先级。 | 发现部门+AI测试 |
| 优化 | 已有功能可用但效率或体验较差 | 进入需求池，按影响人数、频率和业务价值排期。 | 需求部门主管 |
| 新功能 | 新增页面、流程、字段、AI能力或接口 | 必须有业务价值、使用对象、字段清单、验收标准。 | 提出部门主管+老板/AI负责人 |
| 临时报表 | 短期经营分析或管理查看需要 | 必须说明用途、字段、频率、权限；能沉淀则转为正式报表。 | 提出部门主管 |
| 数据导出 | 导出客户、订单、财务、绩效等数据 | 必须审批、脱敏、留痕；敏感导出需更高权限。 | 主管+数据安全负责人 |
| 紧急需求 | 影响成交、收款、投诉、财务结算、数据安全或老板判定紧急 | 主管对接老板确认后进入紧急通道，但上线后必须补齐文档和验收。 | 老板或授权负责人 |

### 10.3 上线验收机制

- 谁提需求，谁参与验收；主管必须确认是否满足部门使用要求。
- 核心流程上线前必须完成测试用例、权限测试、移动端测试、数据回滚或修正方案。
- 部门不配合测试、培训、验收，应进入部门绩效记录，避免系统上线后无人使用。
- 上线后7天内必须观察使用率、Bug、反馈和业务结果，必要时快速修复。

| 备份机制 | 数据库定期备份，关键发布前备份，能恢复。 | 运维安全 |
| 权限体系 | 按岗位、部门、层级、数据敏感度授权。 | 产品+后端+运维 |
| 接口监控 | 企微、小鹅通、金蝶等同步失败要预警。 | 集成/数据工程师 |

## 12. AI治理、数据安全与责任边界

### 12.1 AI调用规则

- 客户手机号、微信、身份证、学历、聊天记录、员工绩效、财务数据可以在不违反安全边界的情况下进入大模型，但默认应做脱敏和权限控制。
- AI生成的职业规划、学习建议、销售话术、质检结论，可按功能设置是否需要人工确认。
- 如果设置了人工审核，AI错误建议导致投诉时责任归审核人；如果没有审核人，责任归AI部门和对应业务规则负责人。
- 每一次AI调用都需要记录调用人、岗位、对象、时间、模型、输入摘要、输出摘要、费用、是否采纳。
- 每个岗位设置每日AI调用预算，超预算需要主管审批。

### 12.2 AI不能直接替代的事项

| 事项 | 规则 |
|---|---|
| 财务审核 | AI可以提示异常、匹配流水、计算佣金，但最终审核必须由财务责任人确认。 |
| 退款审批 | AI可以汇总证据链和风险，但不能自动决定退款。 |
| 质控判责 | AI可以识别过度承诺或异常话术，但质控判责必须由质控负责人确认。 |
| 绩效最终确认 | AI可以统计和预警，但最终绩效由人力和业务负责人确认。 |
| 职业规划/健康建议 | AI可以生成建议草稿，但需要学习规划师或职业规划人员审核后使用。 |

### 12.3 数据安全红线

- 敏感数据导出必须审批、脱敏、留痕。
- 离职员工账号必须及时回收，企微、CRM、课程平台、金蝶、服务器权限都要纳入回收清单。
- 员工只能看到完成岗位工作所需的数据，不因好奇或管理方便扩大权限。
- AI中台成员可以维护系统，但不得随意查看客户隐私、财务敏感数据和员工绩效数据。
- 所有异常访问、异常导出、异常AI调用，都要进入安全审计记录。

## 14. 风险、前置条件与实施建议

### 14.1 主要风险

| 风险 | 表现 | 控制方式 |
|---|---|---|
| 需求失控 | 所有部门都要第一版深度定制，3-8人团队被拖垮。 | 需求工单、优先级、老板审批、第一版深浅分层。 |
| 老板长期被困在产品经理岗位 | 所有业务逻辑都要老板亲自解释，开发无法自主理解。 | 培养产品/业务分析师，沉淀需求模板和业务词典。 |
| 接口目标过重 | 企微、小鹅通、金蝶、直播、电话等同时深度打通导致延期。 | 先关键数据同步，再做深度分析和自动化。 |
| 全栈开发不懂业务 | 页面做出来但不符合岗位实际操作。 | 岗位访谈、验收人制度、AI需求整理、业务培训。 |
| 缺数据治理 | 指标口径混乱，老板大盘不可信。 | 建立指标字典、字段责任人、数据质量评分。 |
| AI使用无边界 | 敏感数据、错误建议、成本失控。 | 脱敏、日志、预算、人工确认、责任规则。 |
| 使用率低 | 系统上线但员工仍用表格和微信。 | 培训通关、主管监督、绩效绑定、低使用率预警。 |

### 14.2 实施建议

- 300万以内保持3-4人，不急于扩编开发，优先把需求、代码、数据库、测试、备份、权限和日志规范建立起来。
- 新增第4人时优先考虑产品/测试实施，而不是简单增加开发，因为当前最大瓶颈是业务需求转译和上线使用。
- 800万以内补到5-6人，重点补产品/业务分析、AI应用/数据、测试实施，让老板逐步退出日常产品经理工作。
- 1600万以内最多8人，形成产品、前端、后端、集成数据、AI、测试实施、运维安全的完整小中台。
- 所有AI功能必须绑定提效目标，不能只做演示效果；上线后要看调用量、采纳率、节省工时和业务结果。
- 外部顾问用于安全、架构、接口、法务、隐私和税务确认，内部团队不必一开始把所有专业能力都招齐。
- 第一版AI-CRM追求能跑通、能使用、能监督、能留痕，不追求所有模块完美。

> **最终判断** 数字产品与AI中台在1600万月营收以内保持8人是可行的，但前提是系统必须高复用、需求必须被管住、业务部门必须承担验收和使用责任、AI必须真正降低重复劳动。否则8人会被所有部门的零散需求吞没。
