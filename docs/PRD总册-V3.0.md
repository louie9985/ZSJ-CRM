## 第 1 章 产品概述

### 1.1 一句话定位

用一套 API-first 模块化单体，沿客户全生命周期（客资→销售→订单→履约→学服→财务→质控→大盘）打通中世健业务，Web + 内部移动端（企微 H5）+ 外部 H5/小程序 三端功能一致，替换老 CRM。〔V3.2/CR-11：原「真 App」改企微 H5〕

## 第 3 章 分册 PRD 标准结构（模板）

每个模块分册 PRD 必须包含以下八节，保证格式统一、可评审、可验收：

```
1. 概述          模块定位、对应总纲章节、批次、验收人、出口标准
2. 用户故事      US-<模块>-<序号>：作为<角色>，我要<动作>，以便<价值>
3. 页面与流程    页面清单（端标注 W/A/双端）、核心操作、主流程图
4. 数据模型      核心表 + 关键字段（引用 PRD-B1 命名规范）
5. 接口概要      关键端点定边界（全量以 OpenAPI 为准）
6. 业务规则      引用 BR 编号（不复制规则正文，引总纲第 5 章）
7. 指标          引用 MT 编号（引总纲第 6 章）
8. 验收用例 AC   可测、有通过标准，对照 BR/MT
9. 边界与不做 + TBD
```

### 3.1 用户故事写法约定

主语必须是第 1.2 节的具体角色；动作必须可落到页面操作；价值对应业务目标。示例：

> US-M4-01：作为新媒体运营，我要用五步向导录入一条客资并自动判重，以便重复客资归属首次提交人、避免撞单（关联 BR-A03）。
> US-M5-01：作为销售，我要在 2 分钟内点击接单、10 分钟内完成首触登记，以便不漏接、不超时（关联 BR-B01、MT-10、MT-11）。

### 3.2 AC 写法约定

参考 PRD-B1 的 AC 表（AC-B1-01 …）。每条 AC 必须能被找 bug 员构造成可执行测试，涉及金额/归属/状态/时效的要写清边界值。示例：

> AC-M4-01：并发抢单——两名销售同时抢同一条抢单池客资，只有一人成功，另一人收到"已被接单"业务错误码（非 500），Ownership 只开一条区间（关联 AP-07、BR-A05）。

## 第 4 章 核心业务流程（跨模块主链路）

五条 E2E 主链路是验收基准，也是分册 PRD 的流程骨架（详见总纲 8.3）：

1. **客资链路**：录入→分配→漏接流转→抢单→接单→首触→有效判定→成交录单（M4→M5→M6）
2. **钱的链路**：订单→报名驳回→补正→通过→财务确认→佣金冻结→7 日解冻（M6→M7→M9）
3. **退款链路**：财务确认→3 日内退款→佣金扣回→责任判定工单闭环（M9→M6→M10）
4. **学服链路**：分班→72h 首触→7 日规划→服务记录→复购机会→复购单→新班分配（M7→M8→M6）
5. **缓考链路**：五级审批→转班→原班关单新班开单（M8）

每条链路的事件流转见《事件契约表》，是模块间唯一的交互契约（AP-21）。

### 5.1 业务规则组（BR，总纲第 5 章）

| 组 | 编号段 | 主题 |
|---|---|---|
| A 客资 | BR-A01~A10 | 等级、判重、自动分配、抢单、公海、无效判定、外部提交者分层可见、兼职收益三段 |

| E 学服 | BR-E01~E09 | 交接分级、触达频率、学员分层、职业种草、复购归属、缓考完整审批链 |

## 第 6 章 分析层需求（M13 大盘）

### 6.1 老板大盘（首页）

一条全生命周期漏斗（今日/本周/本月，支持部门/产品/渠道/销售组切换）+ 五块下钻：经营总览、部门贡献排行、产品经营排行、交付质量、预警区。详见总纲 7.1。

### 6.2 角色大盘

销售组长、新媒体主管、交付主管、报名主管、财务、质控各有核心视图，详见总纲 7.2。

### 6.3 员工个人页

今日待办（可直达处理）+ 个人业绩排名（距上一名差额）+ 我提交的流程状态 + 通知公告 + 反馈入口。详见总纲 7.3。

### 6.4 实时与快照分离

日终快照支撑环比/趋势；实时数字与快照数字分开标注，避免信任问题（总纲 7.4）。
