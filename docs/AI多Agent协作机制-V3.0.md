# AI 多 Agent 协作机制 V3.0

> 读者：技术负责人、3 名全栈工程师、AI 编码代理
> 定位：把"AI 全量辅助编码（token 不限量）"从口号变成一套可运维、可审计、可复现的工程流水线
> 最高约束：总纲第 0 章《架构宪法》AP-01~21 + 《开发手册细则》第 1~4 章
> 配套可落地配置：本仓库 `.claude/`（CLAUDE.md + agents/ 角色定义）

---

## 第 1 章 设计原则

本机制解决一个核心矛盾：**AI 产能近乎无限，但人的评审精力有限、口径需要收敛、架构边界必须守住**。因此设计遵循五条原则：

**原则 1 — 人是决策者，Agent 是产能。** 口径拍板、红线代码放行、架构边界例外，永远由人决定。Agent 负责放大人的产能，不替代人的判断。

**原则 2 — 宪法先行，约束进提示。** 架构宪法 AP-01~21 与开发手册 1~4 章写入每个 Agent 的系统提示。任何 Agent 的产出都以宪法为验收清单，违反直接打回。

**原则 3 — 角色分工，单一职责。** 一个 Agent 只干一件事：产品经理只拆需求不写代码，审查员只挑问题不改代码，找 bug 只报缺陷不实现功能。职责混淆会让质量门禁失效。

**原则 4 — 分级把关，红线人读。** AI 产出分绿/红两级。绿类（UI、DTO、样板 CRUD、测试脚手架）走查即可；红类（金额/佣金、归属、状态机、权限、审批、迁移、定时任务）逐行人读 + 单测强制。

**原则 5 — 可追溯，走工单。** 跨模块边界改动（新增事件、改 platform 接口）先在 M11 开工单，产品负责人批准后才允许 Agent 生成代码。所有协作产出可复现、可回溯到需求来源。

## 第 2 章 角色编排（Agent 组织架构）

### 2.1 组织总览

```
                    ┌─────────────────────────┐
     人（技术负责人）│   决策 / 放行 / 例外裁决  │
                    └───────────┬─────────────┘
                                │ 指令 & 验收
                    ┌───────────▼─────────────┐
                    │  组长 Agent（Orchestrator）│  fable5 / opus4.8
                    │  拆解任务、编排、汇总、把关 │
                    └──┬─────┬─────┬─────┬─────┬┘
             派单 ┌────┘  ┌──┘  ┌──┘  ┌──┘  └────┐ 汇总
          ┌───────▼─┐ ┌───▼───┐ ┌─▼────┐ ┌▼─────┐ ┌▼────────┐
          │产品经理  │ │架构师  │ │实现者 │ │审查员 │ │找 bug 员 │
          │Agent    │ │Agent  │ │Agent │ │Agent │ │Agent    │
          │需求→AC  │ │设计→ADR│ │写代码 │ │挑问题 │ │测边界   │
          └─────────┘ └───────┘ └──┬───┘ └──────┘ └─────────┘
                            codex / sonnet-5（并行多实例）
                                   │
                          ┌────────▼────────┐
                          │ 测试编写 Agent    │（红类：测试先行）
                          └─────────────────┘
```

### 2.2 六大角色职责

| 角色 | 一句话职责 | 输入 | 输出 | 不做 |
|---|---|---|---|---|
| **组长 Orchestrator** | 拆解任务、派单、汇总、对宪法把关、决定是否呈交人评审 | 人的指令 + PRD + 工单 | 子任务派单 + 汇总报告 + 放行建议 | 不亲自写业务代码（可写编排脚本） |
| **产品经理 PM** | 把口径/工单翻译成明确的用户故事与验收用例 AC | 总纲 BR/MT + 工单 | 用户故事、AC 清单、边界与不做、TBD 标记 | 不写代码、不做技术选型 |
| **架构师 Architect** | 模块内设计、接口契约、事件契约、数据模型，守边界 | PRD + 宪法 + 事件契约表 | ADR、接口定义、迁移设计草案、边界检查 | 不写实现细节 |
| **实现者 Implementer** | 按设计与 AC 写代码，测试先行（红类） | 设计 + AC + 事件契约行 | 代码 diff + 单测 + 自审报告 | 不改跨模块边界（需先开工单） |
| **审查员 Reviewer** | 对照宪法清单逐条挑问题，红类逐行 | 代码 diff + 宪法清单 | 问题清单（分级：阻断/建议）+ 打勾表 | 不直接改代码（回给实现者） |
| **找 bug 员 Bug-Hunter** | 主动构造边界/并发/时区/幂等用例找缺陷 | 代码 + AC + 五条 E2E | 缺陷报告 + 复现步骤 + 建议用例 | 不实现功能、不做代码风格评审 |

补充角色（按需启用）：**测试编写 Agent**（红类代码测试先行，人写断言 AC，Agent 补实现）、**文档同步 Agent**（接口变更时同步 OpenAPI/类型/业务文档，落实 AP-15）。

### 2.3 模型分工（角色 ↔ 模型映射）

角色是稳定的，模型是可替换的。下表给出推荐映射，实际以可用模型与成本为准，在 `.claude/agents/*.md` 的 `model` 字段调整。

| 角色 | 推荐模型 | 理由 |
|---|---|---|
| 组长 Orchestrator | **fable5 / opus4.8**（最强推理） | 需要全局把握、复杂拆解、宪法判断、跨角色汇总，用最强模型 |
| 产品经理 PM | opus4.8 / fable5 | 口径理解与歧义识别要求高，需强推理 |
| 架构师 Architect | opus4.8 | 设计权衡、边界判断需强推理 |
| 实现者 Implementer | **codex / sonnet-5**（高性价比、擅长写代码） | 按明确设计写代码，可并行多实例，追求吞吐 |
| 审查员 Reviewer | opus4.8 / fable5 | 审查是质量最后一道闸，用强模型，避免"AI 审 AI"漏网 |
| 找 bug 员 Bug-Hunter | opus4.8 / sonnet-5 | 对抗性思维，中高等模型 |
| 测试编写 Agent | sonnet-5 / codex | 按 AC 写测试，吞吐优先 |

**关键原则**：审查员和实现者不应是同一个模型实例，避免"自己审自己"的盲区；红类代码的审查员建议用比实现者更强的模型。

## 第 3 章 协作流程

### 3.1 标准开发流水线（单个模块/功能）

```
① 人：下达任务（"开发 M4 客资中心 B2 批次"）
        │
② 组长：读 PRD/工单/宪法 → 拆成子任务 → 派单
        │
③ 产品经理：产出用户故事 + AC 清单  ──────┐
        │                                  │ 人评审 AC（口径关）
④ 架构师：产出接口/事件/数据设计 ──────────┤ 人评审设计（边界关）
        │                                  │
⑤ 测试编写：红类先写测试（断言 AC）
        │
⑥ 实现者（codex/sonnet 并行）：按设计写代码 + 补实现让测试通过 + 自审报告
        │
⑦ 审查员：对照宪法清单逐条打勾，红类逐行，产出问题清单
        │
⑧ 找 bug 员：构造边界/并发/时区/幂等用例，产出缺陷报告
        │
⑨ 实现者：修复 → 回到 ⑦ 直到审查通过
        │
⑩ 组长：汇总（宪法打勾表 + 测试结果 + 缺陷闭环）→ 呈交人
        │
⑪ 人：红类逐行评审 → 放行合入（PR 门禁：lint+tsc+单测+boundary+1 人评审）
```

### 3.2 三条关键控制点（人必须在场）

**控制点 A — AC 评审（口径关，步骤③后）**：产品经理产出的 AC 必须由产品负责人确认口径无歧义，尤其涉及 BR/MT 编号的规则。口径漂移在这里拦截，避免下游返工。

**控制点 B — 设计评审（边界关，步骤④后）**：架构师若涉及新增事件或改 platform 接口，必须先在 M11 开工单获批（AP-21）。人确认边界不被破坏。

**控制点 C — 红类放行（合入关，步骤⑪）**：金额/归属/状态机/权限/审批/迁移/定时任务，人逐行读 diff + 确认单测覆盖，才允许合入。

### 3.3 并行策略

**实现者可并行多实例**：同一批次内互不依赖的子任务（如 M4 的不同入口、不同页面）由多个 codex/sonnet 实例并行开发，组长负责拆分无依赖的任务单元并在汇总时检测冲突。

**审查串行、找 bug 并行**：审查员对单个 diff 串行深审；找 bug 员可同时对多个已通过初审的模块跑对抗测试。

**依赖约束**：跨模块只走事件或 platform 服务（不 import），因此模块间天然低耦合，适合并行。同模块内有依赖的子任务（如状态机先于依赖它的业务动作）由组长排序。

## 第 4 章 质量门禁

### 4.1 分级门禁

| 级别 | 范围 | 门禁 |
|---|---|---|
| **绿类** | UI 布局、DTO、样板 CRUD、测试脚手架、文档 | 审查员走查 + CI 自动门禁（lint/tsc/单测/boundary） |
| **红类** | 金额/佣金、Ownership、状态机、权限、审批、迁移脚本、定时任务 | 测试先行 + 审查员逐行 + 找 bug 员对抗 + **人逐行放行** + 单测覆盖率 ≥90% |

### 4.2 宪法打勾表（每个 PR 附带，审查员填写）

审查员对每条相关宪法条款打勾，违反即阻断。示例（完整 21 条见总纲第 0 章）：

```
[ ] AP-01 账号/操作人/员工/任职分开建模，无 God-User
[ ] AP-02 数据范围权限与功能权限分离，未手写 scope where
[ ] AP-03 后端强制鉴权（前端隐藏不算权限）
[ ] AP-04 核心状态/金额/权益由后端判断
[ ] AP-06 历史依赖快照/事件，未用当前配置反推过去
[ ] AP-07 关键动作有前置/互斥/终态保护，防重复/回退
[ ] AP-09 金额/订单/权益有一致性校验、去重、可追溯
[ ] AP-11 定时任务幂等、可重试、有锁、去重
[ ] AP-12 关键动作写审计日志，不记录密码/Token
[ ] AP-18 写操作支持幂等键（request_id）
[ ] AP-19 金额整数分存储计算，禁浮点
[ ] AP-20 配置变更留痕带版本，业务快照记生效配置版本
[ ] AP-21 指标/通知/待办由事件驱动，未跨模块直读表
... （其余条款见总纲）
```

### 4.3 CI 自动门禁（无需人参与，不过不合入）

lint + tsc 类型检查 + 单测全绿 + ESLint boundary 规则（platform 不 import modules、modules 之间不互 import）+ 红类覆盖率阈值 + `MOCK-TODO` 清单每周报告。

### 4.4 AI 自审环节

每个模块完成后，让实现者 Agent 把宪法条款作为检查清单对自己的 diff 逐条自查并输出报告；审查员和人复核该报告。自审不能替代审查员，但能提前暴露低级违规、节省审查精力。

## 第 5 章 上下文与记忆管理

### 5.1 每个 Agent 的系统提示固定包含

1. 架构宪法 AP-01~21 全文（总纲第 0 章）
2. 开发手册细则第 1~4 章（仓库结构、后端规范、前端规范、AI 编码纪律）
3. 目标模块的 PRD 节选 + 相关 AC
4. 事件契约表中与本模块相关的行
5. 角色专属指令（见 `.claude/agents/<role>.md`）

### 5.2 受控文档即共享记忆

总纲、开发手册细则、事件契约表是所有 Agent 的共享事实源。任何 Agent 不得自行发明规则；遇到口径缺失标 TBD，回给人。文档变更走版本递增 + changelog，Agent 每次开工前读最新版本。

### 5.3 跨会话记忆

长期项目知识（已确认口径、踩过的坑、被否决的方案）沉淀到项目记忆/CLAUDE.md，避免每次重新解释。规则被修订时（如复购归属从"保留原规划师贡献"改为"谁成交归谁"）一律采用最后确认版并更新记忆。

## 第 6 章 接口契约披露策略

> 核心原则：**存储用单一事实源，披露用渐进式，中间用 manifest 兜底可发现性。** 存储 ≠ 披露。

### 6.1 为什么区分存储与披露

契约（API + 事件）在磁盘上必须是单一权威源，这是防漂移的根本；但把全量契约灌进每个 Agent 的上下文有两个代价：撑爆 context，以及显著提高 AI 编造字段、张冠李戴的概率。因此磁盘单一源、喂给 Agent 时按需切片。本项目模块间只走事件、天然低耦合，渐进式披露的收益最大。

### 6.2 两类契约的存储（单一事实源）

| 契约 | 权威存储 | 生成/维护方式 |
|---|---|---|
| **API 契约**（端点/DTO/错误码） | OpenAPI spec（由 NestJS 装饰器自动生成） | 代码即契约；CI 产出 shared-core 类型（AP-15），编译期发现变更 |
| **事件契约**（模块间交互） | `事件契约表-V3.0.md`（受控文档） | 人工维护；新增/改字段走 M11 工单 + 产品负责人审批 |

两者都**不拆散、不复制**。规则正文只在这里维护一份，其他文档只引用。

### 6.3 渐进式披露（喂给 Agent 时切片）

Agent 的系统提示**不灌全量契约**，只注入与目标模块相关的切片：

- **架构师/实现者**：只给本模块的端点 + 本模块**发布/订阅**的事件行（如开发 M4 只给 lead 域 + M4 订阅的 ownership.changed 等）。
- **审查员/找 bug 员**：给相关切片 + 边界事件（跨模块订阅点），便于查"该订阅没订阅"。
- **需要更多时**：按 6.4 的 manifest 索引，声明性地拉取指定域/文件的指定段，**不得凭记忆编造**。

### 6.4 契约索引清单（manifest — 渐进式披露的兜底）

渐进式披露最大的风险是 Agent"不知道自己不知道什么"——只看切片会漏掉本该关心的跨切面契约。因此维护一份**契约目录**（`docs/contracts-manifest.md`），它不含契约细节，只回答三个问题：全系统有哪些契约、在哪个文件、需要详情去拉哪一段。

manifest 结构（每行一个契约单元）：

```
| 域/模块 | 契约类型 | 权威文件 | 定位（章节/锚点） | 发布方 | 订阅方 |
|---|---|---|---|---|---|
| lead   | 事件 | 事件契约表-V3.0.md | ## lead 域 | M4/M5 | 调度/M13 |
| order  | 事件 | 事件契约表-V3.0.md | ## order 域 | M5/M8/M4 | M6/M7/M9 |
| M4 API | 接口 | OpenAPI /api/v1/leads | tag: lead | — | — |
| ...    | ... | ... | ... | ... | ... |
```

Agent 拿到任务后：先读 manifest 定位本模块相关的契约单元 → 只拉取这些单元的权威文件对应段 → 发现自己"应该但没有"订阅某事件时，据 manifest 主动补齐或标 TBD 回给组长。manifest 变更与契约变更同步（走 M11 工单），是渐进式披露的"地图"。

### 6.5 防幻觉铁律

- API 以 OpenAPI 生成的类型为准，编译期暴露编造的字段/端点。
- 事件以契约表为准；Agent 不得发明事件名或字段。
- 需要契约详情时按 manifest 拉取权威文件，**不得凭上下文记忆或推测**填充。
- 契约缺失时标 TBD 停推，不自行补全。

## 第 7 章 失败处理与升级

| 场景 | 处理 |
|---|---|
| Agent 产出违反宪法 | 审查员阻断 → 回实现者修复；反复违反同一条 → 升级人，检查提示词是否需强化 |
| 口径歧义/缺失 | 任何 Agent 标 TBD 停止推进该点 → 组长汇总 → 人拍板 → 落 BR/MT 编号 |
| 跨模块边界冲突 | 停止 → 先开 M11 工单 → 产品负责人批准 → 才生成代码 |
| 实现者反复修不好 | 组长换更强模型实例重做，或拆更小任务；仍不行升级人 |
| AI 审 AI 漏网 | 红类强制人逐行；审查员用比实现者更强的模型；找 bug 员独立对抗 |
| 并行任务冲突 | 组长在汇总时检测文件/接口冲突，串行化冲突部分 |
| 幻觉/编造接口 | 以 OpenAPI 自动生成类型为准（编译期发现）；事件以契约表为准 |

**升级红线**：涉及真实客户数据、资金链路、权限变更、不可逆迁移的产出，无论 Agent 多自信，一律人放行。

## 第 8 章 可落地配置说明

本机制的可运行配置放在仓库 `.claude/` 目录：

```
.claude/
  CLAUDE.md              # 项目宪法与规范，注入每个会话/Agent 的上下文
  agents/
    orchestrator.md      # 组长（fable5/opus4.8）
    product-manager.md   # 产品经理
    architect.md         # 架构师
    implementer.md       # 实现者（codex/sonnet-5）
    reviewer.md          # 审查员
    bug-hunter.md        # 找 bug 员
    test-writer.md       # 测试编写
```

每个 `agents/*.md` 含 frontmatter（name/description/model/tools）+ 角色系统提示。使用方式：由组长（主会话）通过任务派发调用对应子 Agent；红类产出汇总后呈交人评审。详见各文件内容与《开发手册细则》第 4 章。

### 使用示例（一次 M4 批次开发）

```
人 → 组长：按 PRD-M4 和事件契约 lead 域，开发 M4 客资中心 B2 批次
组长 → 产品经理：产出 M4 六入口的用户故事 + AC（对照 BR-A01~A10）
  人：评审 AC，确认 BR-A10 判重反馈口径（TBD-2 默认延迟标记）
组长 → 架构师：产出 M4 接口 + lead 域事件落地设计（不新增事件）
  人：确认未破坏边界
组长 → 测试编写：对"2 分钟接单/漏单流转/抢单乐观锁"写测试断言
组长 → 实现者×2（并行）：入口 A/B/C 一组，评级/分配/抢单一组
```
